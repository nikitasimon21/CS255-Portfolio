# CS255-Portfolio
## CS 255: DriverPass System Analysis and Design

### Project Summary

The DriverPass project involved analysing the client's requirements and designing a system to help customers prepare for their driving tests through driving lessons, practice tests, and related services. The proposed system needed to support functions such as customer registration, driving-package purchases, lesson scheduling, reservation management, and administrative oversight. The project focused on translating the client's business requirements into a structured system design.

### What Did I Do Particularly Well?

I believe I did rather well in organising the system requirements and representing the proposed functionality through system design documentation and UML diagrams. Breaking the system into user roles, functions, and workflows helped clarify how customers, secretaries, the owner, and IT administrators would interact with the system. This structured approach made the design easier to understand and provided a foundation for implementation and testing.

### What Would I Revise?

If I could revise one part of my work, I would further refine the system design documentation by examining exceptional situations and alternative workflows in greater detail. For example, reservation conflicts, unavailable instructors, cancelled lessons, and unsuccessful login attempts could be documented more thoroughly. Adding these scenarios would make the design more comprehensive and help developers anticipate potential problems before implementation.

### Understanding and Implementing User Needs

I approached the project by identifying the client's objectives and translating them into system requirements and functional workflows. The design considered the needs of customers who schedule lessons, secretaries who manage reservations, the owner who reviews reports and driving progress, and IT administrators who manage accounts and access rights. Considering user needs is essential because a system may function correctly from a technical perspective while still failing to address the practical requirements of the people who use it.

### My Approach to Software Design

My approach to software design begins with understanding the problem, identifying stakeholders, gathering requirements, and defining the system's functional and non-functional expectations. I then use techniques such as UML use case diagrams, activity diagrams, and sequence diagrams to represent system behaviour and interactions before implementation. In future projects, I would also place greater emphasis on validating requirements with stakeholders, documenting exceptional cases, reviewing security and accessibility requirements, and incorporating feedback throughout the design process. These practices help produce systems that are maintainable, reliable, and aligned with user expectations.
